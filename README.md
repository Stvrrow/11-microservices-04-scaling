# Домашнее задание к занятию «Микросервисы: масштабирование» — Стрельников Александр

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.

## Задача 1: Кластеризация

Предложите решение для обеспечения развёртывания, запуска и управления приложениями.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- поддержка контейнеров;
- обеспечивать обнаружение сервисов и маршрутизацию запросов;
- обеспечивать возможность горизонтального масштабирования;
- обеспечивать возможность автоматического масштабирования;
- обеспечивать явное разделение ресурсов, доступных извне и внутри системы;
- обеспечивать возможность конфигурировать приложения с помощью переменных среды, в том числе с возможностью безопасного хранения чувствительных данных таких как пароли, ключи доступа, ключи шифрования и т. п.

Обоснуйте свой выбор.

**Решение:**

Предлагаю **управляемый Kubernetes в облаке**: containerd на рабочих узлах, Service/CoreDNS для обнаружения сервисов, Gateway API с установленным контроллером (например, Envoy Gateway) для внешнего HTTP(S), HPA для приложений, autoscaler облачных групп узлов для вычислительных ресурсов. CNI с поддержкой NetworkPolicy обеспечивает сетевую изоляцию.

| Требование | Реализация |
|---|---|
| Контейнеры | Приложения упаковываются в OCI-образы, загружаются в Registry и запускаются в Pod через containerd. Deployment поддерживает нужное число реплик и rolling update. |
| Обнаружение сервисов и маршрутизация | Service типа ClusterIP даёт стабильное имя/адрес, CoreDNS — DNS-имя. EndpointSlice содержит готовые endpoint. HTTPRoute через Gateway направляет внешние запросы по host/path к Service. Gateway API требует отдельного контроллера, сами CRD трафик не обрабатывают. |
| Горизонтальное масштабирование | Изменение `Deployment.spec.replicas` или `kubectl scale` увеличивает число Pod; Service направляет трафик на готовые реплики. Реплики распределяются между узлами/зонами через topology spread constraints. |
| Автоматическое масштабирование | HPA (`autoscaling/v2`) меняет число Pod по CPU/RAM или метрикам нагрузки. Metrics Server предоставляет resource metrics; Prometheus Adapter — custom/external metrics. Autoscaler группы узлов добавляет узлы, когда Pod не помещаются на существующих. |
| Разделение внешних и внутренних ресурсов | Только публичный Gateway доступен через внешний LoadBalancer; API, БД, брокеры и exporters используют ClusterIP/приватные адреса. NetworkPolicy запрещают трафик по умолчанию и разрешают нужные связи. |
| Настройки и секреты | ConfigMap и `env`/`envFrom` для обычных настроек, Secret через `secretKeyRef` или volume для чувствительных данных. Источник секретов — Vault/облачный Secret Manager с выдачей по workload identity и синхронизацией в кластер. |

**Схема взаимодействия:**

```text
Клиент → HTTPS LoadBalancer → Gateway/HTTPRoute → Service ClusterIP → Pod приложения
                                                            ↓
                                                внутренние Service: БД/брокер

Registry → containerd → Pod
Metrics Server / Prometheus Adapter → HPA → число Pod
Pending Pod → autoscaler группы узлов → новые узлы
Secret Manager → контроллер секретов → Secret → Pod
```

**Как это будет работать:**

1. CI собирает образ, тестирует его и публикует в Registry. Изменение digest в Git конфигурации окружения применяется Argo CD. Получается продолжение процесса разработки из [задания 03](../11-microservices-03-approaches/README.md).
2. Deployment запускает несколько реплик приложения. `startupProbe` даёт время на инициализацию, `readinessProbe` исключает неготовые Pod из Service, `livenessProbe` перезапускает зависший контейнер. Rolling update задаёт допустимые `maxSurge` и `maxUnavailable`.
3. Например, для API HPA держит от 3 до 12 реплик при целевой загрузке CPU 60% от `requests.cpu`. У контейнеров задаются CPU/memory requests; без корректных requests процент CPU не будет полезным сигналом. Стабилизация scale-down уменьшает колебания числа реплик. Для воркеров лучше масштабирование по длине очереди или отставанию потребителя.
4. Если HPA создал больше Pod, чем помещается на узлах, autoscaler расширяет пул в рамках квот и максимума. HPA сам не добавляет серверы, а добавление сервера не происходит мгновенно: нужны запас ёмкости и разумный минимум реплик.
5. Все пользовательские запросы проходят через публичный Gateway с терминацией TLS. Внутренние сервисы не получают NodePort или публичный LoadBalancer. NetworkPolicy разрешают Gateway обращаться к API, API — к БД/брокеру и DNS, сборщикам — к endpoints метрик; остальные связи закрыты. Namespace помогает разделять команды и окружения, но сам по себе сетевой границей не является.
6. Секреты выдаются только нужному ServiceAccount и namespace, доступ ограничивается RBAC. Включается шифрование Secret в etcd через KMS/encryption at rest; base64 в Secret не является шифрованием. В Git хранятся ссылки на секреты, а не значения. При изменении Secret, переданного через переменную среды, требуется перезапуск Pod; при файловом монтировании приложение должно уметь перечитывать значение.

**Условия масштабирования:** API не хранит сессии и файлы в памяти/локальном диске отдельной реплики: сессии выносятся во внешнее хранилище, файлы — в объектное. Повторные запросы и обработка сообщений проектируются идемпотентными. Для БД и брокеров нужны собственные репликация и резервное копирование: увеличение `replicas` у приложения не масштабирует их автоматически. StatefulSet задаёт идентичность и тома Pod, но сам не превращает базу данных в отказоустойчивый кластер.

Рабочие узлы размещаются в приватных сетях, доступ к Kubernetes API ограничивается, задаются ResourceQuota и LimitRange. PodDisruptionBudget ограничивает добровольное одновременное выселение реплик, но не предотвращает аварийную потерю узла. Отказоустойчивый control plane обслуживает облачный провайдер, настройки приложений, сети и восстановления остаются ответственностью команды.

**Почему Kubernetes:** он закрывает все требования стандартными API и даёт общую платформу для независимых сервисов. Managed-вариант уменьшает объём обслуживания control plane. Docker Compose удобен для локальной разработки, но не даёт полноценного управления многоузловым кластером и автоскейлинга. Более простой оркестратор тоже возможен, однако для крупной компании Kubernetes удобен совместимостью с GitOps, мониторингом, политиками и облачной инфраструктурой. Цена выбора — необходимость компетенций и сопровождения контроллеров.
